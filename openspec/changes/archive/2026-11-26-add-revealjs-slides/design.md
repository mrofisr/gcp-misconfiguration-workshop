# Design

## Context

See `proposal.md` for motivation and `specs/` for the behavior contract. The repository currently contains only documentation-style workshop material under `workshop/`; `workshop/slides/outline.md` is the authoritative 90-minute agenda with seven timed segments and per-segment notes. The user chose a **new top-level `slides/`** directory for the deck, a **Google Sans CSS stack with graceful fallbacks** (no bundled font files), and the canonical **Anatomy skill repository** as the figure generator.

Verified external facts used in this design (2026-11):

- reveal.js offers a "basic setup" with a distributed build that needs no build tools, plus a full npm setup whose development server requires Node.js 20.19+; its print/PDF path uses the `?print-pdf` query parameter and browser print dialog. Source: <https://revealjs.com/installation/> and <https://revealjs.com/pdf-export/>
- The Anatomy skill is a standard Agent Skill at `https://github.com/wheresryan22/anatomy`; OpenCode installation is `npx skills add wheresryan22/anatomy -g -a opencode` (into `~/.config/opencode/skills/anatomy`). Its kit needs Node.js 20.10+, uses only built-in modules, and its `scripts/inline-kit.mjs` produces standalone HTML pages; browser verification needs Chrome or Chromium. Source: <https://github.com/wheresryan22/anatomy>
- Google Sans is a proprietary Google font and is not distributed by the public Google Fonts API; Google Sans Code is a separate open-source family. Source: <https://fonts.google.com/>

## Goals / Non-Goals

**Goals:**

- Produce a deck that can be presented from a plain static server with no build, install, or internet access at session time.
- Mirror the seven-segment agenda exactly, with speaker notes derived from the outline's segment notes.
- Give beginners three tangible, interactive visual explanations generated by the Anatomy skill.
- Keep typography consistent with the Google Sans stack and degrade safely without it.
- Make a print/PDF version of the deck that still shows every figure.

**Non-Goals:**

- Rewriting or extending the workshop curriculum, lab guides, or starter repository.
- Adding a general-purpose figure pipeline beyond the three deck figures.
- Redistributing Google Sans font files or fetching any font at runtime.
- Building a custom presentation framework, a slide server with authentication, or a hosted/published deck.
- Generating figures live during the workshop session.

## Decisions

### 1. Pinned, vendored reveal.js basic setup instead of an npm build

Commit the reveal.js distribution files (core CSS/JS and only the needed plugins) under `slides/vendor/`, pinned to a tagged release recorded in `slides/README.md`. Slides are authored as HTML sections in `slides/index.html`, initialized with a small inline script; no `package.json` or bundler is introduced. Presenting uses a local static HTTP server rooted at `slides/`.

- **Why:** The repository is documentation-first, participants need the deck to work offline, and the basic setup needs no Node or install at session time. A static server (rather than `file://`) is required anyway for same-origin iframe figures.
- **Alternatives:** npm-based setup with `npm install` and `npm start` (rejected: build/install step and Node 20.19+ at presentation time); CDN script tags (rejected: fails the offline requirement); authoring slides in Markdown via the plugin (rejected: adds a plugin dependency and complicates precise iframe placement).

### 2. One horizontal slide per segment, vertical slides for detail

Use the seven segments as top-level slides. Within a segment, use vertical slides only where needed: a title/key-message slide, an explainer slide, and a figure or checkpoint slide. The opening slide carries the agenda table with all seven durations; each segment banner repeats its allotted time. Segment notes from `workshop/slides/outline.md` become `<aside class="notes">` content.

- **Why:** Keeps the deck aligned with the facilitator's timing and avoids introducing new lab steps.
- **Alternatives:** A flat sequence of many slides (rejected: loses the segment structure the facilitator paces against); a separate slide file per segment (rejected: more files to synchronize and no benefit for a static deck).

### 3. Anatomy figures generated ahead of time, installed for OpenCode

Install the skill globally with `npx skills add wheresryan22/anatomy -g -a opencode`. Author three figures — bucket/IAM guest list (segment 2), public bucket plus over-permissive permission (fix 1), and hardcoded key plus unsafe file name (fix 2) — as small build scripts under `slides/figures/src/`. Each build script uses the skill's kit to emit a standalone HTML page under `slides/figures/` with inline styles and scripts, plus a static SVG poster. Generated artifacts are committed so presenting needs no Node, skill install, or Chrome; regeneration requires Node 20.10+ and the installed skill, documented in the README.

- **Why:** Anatomy explains by building a working object, which fits these concepts, and its standalone HTML output matches the offline requirement. Committing output keeps `slides/` self-contained.
- **Alternatives:** Hand-drawn SVG diagrams (rejected: static and less explanatory than a model-driven figure); loading figures from a CDN or the skill repo at runtime (rejected: offline requirement); generating figures live in the session (rejected: slow, needs Node and Chrome on the presenting machine).

### 4. Iframe embeds with a print/reduced-motion swap

Embed each standalone figure with an `<iframe>` sized to the slide, marked `data-prevent-swipe` so touch interaction does not move the deck, and give it a fixed aspect-ratio container so it fits both projector and laptop viewports. A print stylesheet swaps the iframe for the committed static SVG, and the figure itself honors `prefers-reduced-motion` by presenting a still state.

- **Why:** Browsers do not reliably print iframe contents, and reveal.js captures swipe gestures that figures also want; both need an explicit boundary.
- **Alternatives:** Inlining figure markup into the slide (rejected: couples figure state to deck state and makes regeneration fragile); showing screenshots only (rejected: loses interactivity, which is the point of using Anatomy).

### 5. Typography without font files

Set `font-family: 'Google Sans', 'Google Sans Code', Roboto, sans-serif` on `.reveal` and inherit everywhere; define no `@font-face` rule and add no `<link>` to a font service. Choose the reveal.js light theme (or a minimal custom theme based on it) for projector contrast, with slide text sized and wrapped to remain inside bounds when a fallback font is used.

- **Why:** Google Sans cannot be legally bundled from the public font API, and the user chose a CSS stack with fallbacks. Testing the fallback path is the only way to guarantee readable slides on unknown machines.
- **Alternatives:** Self-hosting Google Sans files (rejected by user); using only Google Sans Code (rejected by user); loading Google Sans from a third-party CDN (rejected: licensing and offline constraints).

### 6. Export through reveal.js print mode

Document the export path as opening `slides/index.html?print-pdf` in Chromium and saving to PDF with background graphics enabled. Add an automated check that the deck's segment titles/durations match `workshop/slides/outline.md` and that every figure slide has a static alternative.

- **Why:** It uses reveal.js's supported export path without extra dependencies, and the check prevents the deck from drifting from the authoritative agenda.
- **Alternatives:** A separate PDF checked into the repo (rejected: another artifact to synchronize); a screenshot-based export tool (rejected: extra dependency and poor text selectability).

## Risks / Trade-offs

- **Google Sans is absent on the presenting machine** → Mitigation: declared fallback stack, and verification at projector and laptop sizes with the fallback font active.
- **Figure interaction changes the slide** → Mitigation: `data-prevent-swipe` on iframe containers and an explicit check of pointer and keyboard interaction inside each figure.
- **Print/PDF shows blank figure areas** → Mitigation: committed static SVG poster per figure, swapped in by the print stylesheet and verified in a sample PDF.
- **Anatomy figures take a long session to build and verify** → Mitigation: limit to three figures, reuse one kit and one camera, and use the skill's geometry audit/browser capture only on the final versions.
- **Vendored reveal.js files add repository weight** → Mitigation: pin one release and include only the distribution files the deck actually loads.
- **Deck drifts from the outline** → Mitigation: keep the outline as source of truth and run the title/duration consistency check before declaring the deck ready.
- **Proprietary font licensing** → Mitigation: no font files are added; the README states that Google Sans must already be installed to be used.

## Migration Plan

Greenfield for the deck; no data migration and no change to existing workshop files. Delivery sequence:

1. Create `slides/` and vendor a pinned reveal.js distribution plus a minimal theme.
2. Author `slides/index.html` from `workshop/slides/outline.md`, including agenda, notes, and figure placeholders.
3. Install the Anatomy skill for OpenCode and generate the three standalone figures plus static posters under `slides/figures/`.
4. Embed the figures, add the typography and print/reduced-motion rules, and write `slides/README.md`.
5. Verify local serving, keyboard/touch navigation, figure interaction isolation, fallback-font layout, and a sample PDF export.

Rollback is to withhold the new `slides/` directory; no existing artifact depends on it.

## Open Questions

Deferrable without changing specs, approach, or tasks:

- Whether to publish the deck to GitHub Pages after the session (the offline local deck remains the contract).
- Whether a future Indonesian-language version of the slides is needed (the current outline is English).
- Exact figure color accents, as long as the light theme, captions, and contrast requirements hold.
